# Licensing and attribution

## Publicly available assets

“Publicly available” does not mean “free to redistribute.” For each downloaded
asset, record the author, exact source URL, version or commit, license name,
and any required notices or restrictions. Check whether the license allows
bundling the asset in an installer and whether its notices must ship with the
binary. Keep the original license text in `licenses/` and add a mapping to
[`THIRD_PARTY_NOTICES.md`](../THIRD_PARTY_NOTICES.md).

The bundled font families have been traced to their upstream projects and are
distributed under OFL-1.1. Their notices and license files are included in the
installer. The existing icons, theme previews, and pet sprite assets still
need source and redistribution-rights confirmation; do not assume their
license from appearance alone.

## Content generated with an AI tool

AI generation does not automatically attach an open-source license to an
asset, guarantee copyright ownership, or clear third-party rights. Review the
terms of the specific generation service and the laws that apply to the
project. Also review the output for recognizable protected material. Keep a
short record of the tool, generation date, prompt or production notes, and any
human editing. Only label an asset project-created when its actual provenance
is known.

The two README theme illustrations are new hand-authored SVG artwork made for
this repository; they contain no application screenshot or user conversation.

## Project source and code license

There is currently no root `LICENSE` covering the whole project. The installer
package metadata declares MIT for that package, but that does not clearly
license all runtime code, artwork, and other files. The repository owner must
choose the intended project-wide license and scope before announcing a public
source release. Third-party material keeps its own license regardless of that
choice.
